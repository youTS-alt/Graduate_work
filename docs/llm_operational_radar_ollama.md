# LLM-модуль: «Операционный радар» (основа — Ollama)

Этот документ описывает, как должен работать модуль LLM, который генерирует блок **«Рекомендации ИИ»** на главной странице как **общий операционный радар** (операционные next-steps по состоянию отеля/CRM).

## 1) Цель и продуктовый контракт

**Цель:** превратить “срез состояния” CRM (тикеты, задачи, бронирования, аудит) в короткий список **конкретных действий**, которые помогут команде быстрее закрывать риски и не пропускать важные ситуации.

**Что показываем на главной:**
- 3–7 рекомендаций, отсортированных по важности.
- У каждой рекомендации: короткий заголовок, причина (почему важно), действие (что сделать), ссылка на сущность (если применимо), риск/приоритет, флаг “нужно подтверждение”.

**Не цель:** чат-бот на главной. Главная — это “дашборд + next actions”, а не переписка.

## 2) Архитектура (высокоуровнево)

1. **Сбор снапшота (radar_snapshot)** из БД (агрегаты + top-N проблемных записей).
2. **LLM-генерация** рекомендаций на основе снапшота через Ollama.
3. **Валидация формата** ответа (строгий JSON).
4. **Сохранение результата** (отдельная таблица/модель отчёта) + метаданные (модель, время, хэш снапшота).
5. **Отображение** последнего успешного отчёта на главной странице.

Рекомендуемый режим: генерация в фоне по расписанию (каждые N минут) + кнопка “Обновить радар” (опционально).

## 3) Источники данных для радара

Снапшот должен быть компактным. Задача — дать LLM достаточно контекста для приоритизации, но не выгружать “всё подряд”.

### 3.1 Тикеты (Ticket / TicketMessage)
- Открытые/в работе/ожидание.
- Просрочки SLA (если есть), “без ответа X минут/часов”.
- Высокий приоритет, VIP-сегмент клиента, эскалации.
- Последнее входящее сообщение (коротко), канал, когда обновлялось.

### 3.2 Задачи (Task)
- Просроченные.
- `failed`.
- Без исполнителя.
- Долго в `in_progress`.
- Связанные с тикетами/бронированиями (чтобы LLM могла связать причину и действие).

### 3.3 Бронирования (Booking)
- Заезды сегодня/завтра, ранние/поздние выезды (если есть поля).
- Неоплаты/подтверждения/отмены.
- Конфликты/овербукинг (если реализовано).
- Особые пожелания (в кратком виде).

### 3.4 Аудит и действия агента (Audit / AgentActionLog)
- Последние действия “ИИ” и оператора.
- Действия, требующие подтверждения.
- Что было отклонено или не подтверждено.

### 3.5 Политики / правила (если есть)
Передаются как краткий список ограничений (“компенсации > X требуют апрува”, “нельзя обещать Y без подтверждения”).

## 4) Privacy-by-design (минимизация ПДн)

**Правило:** в снапшот не включать лишние ПДн и не отправлять их в LLM без необходимости.

Рекомендации:
- Вместо email/телефона — внутренние `id` и/или “клиент #123”.
- Имена гостей можно сокращать (например, “Анна С.”) или заменять на `client_id`, если UI всё равно открывает карточку по id.
- Тексты сообщений — обрезать до 240–500 символов и убирать чувствительные фрагменты (регулярки на телефоны/почты/номера карт).

## 5) Формат снапшота (пример схемы)

Снапшот — это JSON, который строится строго из понятных полей и агрегатов. Пример (упрощённо):

```json
{
  "generated_at": "2026-03-24T10:30:00+03:00",
  "timezone": "Europe/Moscow",
  "kpis": {
    "open_tickets": 18,
    "high_priority_tickets": 4,
    "overdue_tasks": 7,
    "today_checkins": 12,
    "today_checkouts": 9
  },
  "top_tickets": [
    {
      "id": 201,
      "status": "open",
      "priority": "high",
      "updated_at": "2026-03-24T10:25:00+03:00",
      "client_id": 5,
      "booking_id": 101,
      "subject": "Поздний выезд",
      "last_inbound_excerpt": "Можно ли выехать в 16:00?"
    }
  ],
  "top_tasks": [
    { "id": 88, "status": "failed", "due_at": "2026-03-24T09:00:00+03:00", "assignee_id": null, "ticket_id": 201 }
  ],
  "top_bookings": [
    { "id": 101, "status": "confirmed", "checkin_date": "2026-03-24", "checkout_date": "2026-03-28", "client_id": 5 }
  ],
  "policies": [
    { "key": "compensation_limit", "rule": "Компенсации > 5000 ₽ требуют подтверждения" }
  ]
}
```

## 6) Контракт ответа LLM (строгий JSON)

LLM должна возвращать **только JSON** в заранее оговорённой структуре.

Рекомендуемый формат:

```json
{
  "items": [
    {
      "title": "Ответить гостю по позднему выезду",
      "why": "Тикет #201 без ответа 45 минут, высокий приоритет (VIP).",
      "action": "Открыть тикет и отправить подтверждение/альтернативу по позднему выезду.",
      "entity": { "type": "ticket", "id": 201 },
      "risk": "high",
      "needs_approval": true,
      "tags": ["SLA", "VIP", "late_checkout"]
    }
  ],
  "summary": "3 главных фокуса на ближайший час: SLA по VIP, 2 просроченные задачи, заезды сегодня.",
  "model_notes": "Если нет фактов — не выдумывай; предлагай проверку."
}
```

Правила:
- `risk`: `low|medium|high`.
- `needs_approval`: `true`, если рекомендация предполагает компенсации/скидки/нестандартные обещания/рисковые действия.
- `entity`: может быть `null`, если рекомендация общего характера (“проверить очередь”).

## 7) Промптинг: системные инструкции и стиль

### 7.1 System prompt (намерение)
- Роль: “операционный менеджер отеля/CRM”.
- Приоритет: конкретика, краткость, проверяемость.
- Запрет: не выдумывать факты, не “галлюцинировать” отсутствующие поля.
- Выход: только JSON заданной схемы.

### 7.2 User prompt (данные)
- Вставляем `radar_snapshot` как JSON.
- Указываем ограничения: количество рекомендаций (3–7), язык (ru), таймзона.

## 8) Интеграция с Ollama

### 8.1 Требования
- Ollama запущена локально или в сети (например, `http://localhost:11434`).
- Выбранная модель скачана (например, `llama3.1`, `qwen2.5`, `mistral` — выбор зависит от качества/скорости).

### 8.2 API вызов (пример)

Обычно используется endpoint чата:
- `POST /api/chat`

Пример запроса (концептуально):

```json
{
  "model": "llama3.1",
  "stream": false,
  "messages": [
    { "role": "system", "content": "<system prompt>" },
    { "role": "user", "content": "<user prompt + radar_snapshot>" }
  ],
  "options": {
    "temperature": 0.2
  }
}
```

### 8.3 Параметры качества
- `temperature`: 0.0–0.3 (для стабильного JSON и меньше “креатива”).
- Ограничивать длину ответа (если поддерживается), чтобы не раздувать JSON.

## 9) Обновление и кеширование

Рекомендуемая стратегия:
- Генерировать радар раз в 5–15 минут.
- Считать `snapshot_hash` (например, SHA-256 от нормализованного JSON снапшота).
- Если `snapshot_hash` не изменился — не дергать LLM.
- Хранить последние N отчётов (например, 100–500) для аудита и отладки.

## 10) Отказоустойчивость

Если LLM недоступна или ответ невалиден:
- Показывать последний успешный отчёт + метку “устарел”.
- Логировать причину (таймаут/HTTP ошибка/невалидный JSON).
- Не блокировать загрузку главной страницы.

## 11) Безопасность и контроль рисков

Минимальный набор защит:
- Санация снапшота (маскирование ПДн, обрезка текстов).
- Детектор “опасных действий” (компенсации, юридические обещания, финансовые операции) → `needs_approval=true`.
- Запись всех рекомендаций в аудит (кто/когда/какая модель/какой снапшот).

## 12) План внедрения (итерациями)

1. Модель хранения отчёта “OperationalRadarReport”.
2. Сбор `radar_snapshot` на бэке (агрегаты + top-N).
3. Генерация через Ollama (без стрима, строгий JSON).
4. Показ на главной вместо захардкоженного списка.
5. Кнопка “Обновить” + фон-расписание.
6. Guardrails + тесты на валидацию JSON и маскирование.
